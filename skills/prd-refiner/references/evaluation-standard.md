# PRD 优化前后评价标准

本标准用于回答“优化后是否比原始需求更好”。原始 PRD 与优化后 PRD 必须使用同一量表、同一需求范围和同一证据边界评分。评价不以篇幅、章节数量或文字美观为主要依据，而以信息质量和下游可用性为依据。

## 1. 评分方法

每个评价维度按 0–4 分评分：

| 分值 | 通用含义 |
|---|---|
| 0 | 缺失，或内容严重冲突，无法用于决策或实现 |
| 1 | 有零散描述，但关键条件、规则或来源大量缺失 |
| 2 | 基本可理解，仍需较多人工猜测或补充确认 |
| 3 | 大部分完整、明确、可追溯，仅有少量非阻塞问题 |
| 4 | 完整、明确、一致、可验证，可直接支持评审和下游任务 |

加权得分公式：

`总分 = Σ（维度得分 ÷ 4 × 维度权重）`

总分范围为 0–100。评分必须附证据位置和扣分原因，不能只填数字。

## 2. 评价维度与权重

| 维度 | 权重 | 重点证据 |
|---|---:|---|
| 完整性 | 25 | 十二维覆盖情况；角色、条件、流程、规则、异常、边界、权限、状态、验收和非功能是否充分 |
| 清晰性 | 15 | 主体、触发、动作、结果、例外是否明确；是否存在“快速、正常、支持”等不可验证表达 |
| 一致性 | 12 | 术语、数值、流程、权限、状态、PRD 与原型之间是否冲突 |
| 可追溯性 | 12 | 关键结论是否关联来源或 `CL-xxx`；需求、`UI-xxx`与验收是否建立双向关联 |
| 可测试性 | 15 | 主流程、异常、边界、权限、状态和非功能是否可形成测试条件和预期结果 |
| AI 可消费性 | 10 | AI 是否无需猜测即可提取功能、规则、状态、异常、依赖和验收 |
| 人工可理解性 | 6 | 产品、研发和品质是否能快速定位范围、规则、未决项和影响 |
| 下游可用性 | 5 | 是否可用于任务拆分、技术方案、测试点生成和 AI Coding 输入准备 |
| **合计** | **100** |  |

## 3. 各维度评分锚点

### 3.1 完整性（25）

- 0：核心目标或功能不可辨识。
- 1：只有功能概述，角色、条件、异常、边界、权限、状态和验收大多缺失。
- 2：主流程可理解，但十二维中仍有多个关键维度缺失或未标记。
- 3：十二维均有结论，少量非阻塞项待确认。
- 4：十二维完整覆盖，适用项充分，不适用项有理由，未决项影响透明。

### 3.2 清晰性（15）

- 0：大量歧义或相互矛盾，无法形成一致理解。
- 1：依赖主观词和隐含规则，需要频繁口头解释。
- 2：主要功能明确，部分条件、例外、字段或反馈仍模糊。
- 3：绝大多数规则按主体、条件、动作、结果、例外表达。
- 4：关键规则无实质歧义，术语、单位、状态和反馈均有定义。

### 3.3 一致性（12）

- 0：核心规则互相冲突且没有决策。
- 1：存在多处术语、流程、数值或原型冲突。
- 2：主要冲突已发现，但仍有未处理或未标记问题。
- 3：冲突已处理或透明列为待确认，仅有轻微编辑问题。
- 4：跨章节、跨来源和跨状态完全对齐，决策链清楚。

### 3.4 可追溯性（12）

- 0：无法判断结论来源。
- 1：只有文档级来源，规则和决策无法逐项回溯。
- 2：部分需求有来源或编号，链路不完整。
- 3：关键需求、规则和验收有来源及关联 ID。
- 4：需求—来源—澄清—验收链路完整，变更也能定位。

### 3.5 可测试性（15）

- 0：无法形成测试条件和预期结果。
- 1：只有“功能正常”等笼统验收。
- 2：主流程可测，异常、边界、权限或状态覆盖不足。
- 3：关键路径和高风险边界均有可验证标准。
- 4：需求与验收双向关联，可直接形成系统化测试设计。

### 3.6 AI 可消费性（10）

- 0：AI 无法稳定提取任务或会产生相互矛盾解释。
- 1：需要大量猜测角色、条件、状态和例外。
- 2：可提取主要功能，但任务拆分或测试点结果不稳定。
- 3：结构和 ID 稳定，少量未决项已明确标记。
- 4：AI 可稳定生成需求清单、任务拆分和测试点，且不会把待确认项当事实。

### 3.7 人工可理解性（6）

- 0：主要干系人无法形成一致理解。
- 1：需要作者持续口头补充。
- 2：可阅读但定位规则、风险和决策较慢。
- 3：主要信息容易定位，未决风险清晰。
- 4：产品、研发和品质能快速完成评审并引用具体 ID。

### 3.8 下游可用性（5）

- 0：不能作为任何下游工作的可靠输入。
- 1：只能用于背景了解。
- 2：可辅助任务拆分，但仍需要大量二次需求确认。
- 3：可支持任务拆分、测试设计或技术方案中的多数工作。
- 4：可直接作为多个下游任务的受控输入，并明确其限制。

## 4. 过程红线

出现以下任一情况时，即使总分较高，也不能判定为“达到优化目标”：

1. AI 推测被写成产品经理已确认规则；
2. P0 阻塞问题未解决且未醒目标记；
3. 原始 PRD 与原型的关键冲突被静默覆盖；
4. 来源、需求、交互、澄清和验收之间无法追溯；
5. 优化后改变原始业务意图，但没有产品经理确认；
6. 只评价优化后文档，没有按同一量表评价原始文档。

## 5. 效果判定

| 判定 | 条件 |
|---|---|
| 显著改善 | 总分提升不少于 20 分；完整性、清晰性、可测试性均提升；无过程红线 |
| 有效改善 | 总分提升 10–19.9 分；核心维度不下降；无过程红线 |
| 轻微改善 | 总分提升 1–9.9 分，或主要改善集中在格式和可读性 |
| 无明显改善 | 总分不变或下降，或仍存在未处理过程红线 |

建议同时记录：P0/P1 问题数量、已确认 `CL-xxx` 数量、十二维覆盖率、可验证验收数量、无来源关键规则数量和下游任务人工追问次数。案例数量较少时应报告事实和差异，不做统计显著性宣称。

## 6. 评价操作要求

1. 固定同一需求范围和同一批输入材料。
2. 先对原始资料评分并冻结结果，再查看优化后文档评分，减少结果倒推。
3. 尽量由产品、研发、品质至少两个角色独立评分；分差超过 1 分时记录原因并复核。
4. 每一分必须引用证据；不能因文档更长或使用更多标题而加分。
5. 下游对比使用相同 AI 工具、模型、提示和任务，例如功能提取、任务拆分或测试点生成。
6. 将仍未改善的维度转为规范、流程或插件的下一轮改进项。
