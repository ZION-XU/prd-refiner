# PRD 优化规范

本规范定义 PRD Refiner 面对任意样式人工 PRD 时的统一检查和归一化方法。输入文档可以是 Word、Markdown、表格、邮件、会议记录、截图说明或混合材料，不要求原文采用固定模板。优化的目标不是保留原文版式，而是在不改变已确认业务意图的前提下，建立完整、清晰、一致、可验证和可追溯的需求基线。

## 1. 规范原则

1. **内容优先于版式**：标题、表格或字段名只作为线索，不能假定原文结构完整。
2. **证据优先于推测**：只把原始事实、原型观察和产品经理确认写入确定性结论。
3. **缺失必须可见**：没有说明的关键内容标记为“待确认”，不得静默省略或补造。
4. **冲突必须决策**：PRD、表格、截图、原型和口头说明不一致时，创建独立澄清项。
5. **规则必须可执行**：使用明确的主体、条件、动作、结果、例外和来源。
6. **输出必须可追溯**：需求、规则、数据、非功能和验收项使用稳定 ID，并关联来源或 `CL-xxx`。

## 2. 任意格式输入的归一化

### 2.1 建立来源清单

为每份输入分配来源编号，例如 `SRC-PRD-01`、`SRC-TABLE-01`、`SRC-PROTOTYPE-01`、`SRC-IMAGE-01`。记录文件名或链接、版本、日期、可访问范围和解析限制。

### 2.2 按语义切分而非按版式照搬

逐段提取以下语义单元：目标、范围、角色、条件、动作、规则、数据、状态、权限、异常、边界、非功能、验收、依赖和未决事项。一个原文段落可以拆成多个语义单元；分散在多处的同一规则需要合并并保留全部来源。

### 2.3 建立证据台账

| 证据类型 | 定义 | 可否写成最终规则 |
|---|---|---|
| 原始事实 | PRD、表格、附件或正式说明明确陈述 | 可以，保留来源 |
| 原型观察 | 截图或可访问原型中直接可见的界面、文案、状态和连接 | 可以写成观察；冲突时必须澄清 |
| 产品经理确认 | 对澄清问题的明确回答 | 可以，优先级最高 |
| AI 建议 | AI 提出的候选规则、风险或改进方案 | 不可以，确认后转为产品经理确认 |
| 待确认 | 缺失、模糊、冲突、无法访问或责任不清的信息 | 不可以，保留风险和责任人 |

产品经理确认可以解决冲突，但不得删除原始冲突记录。技术实现建议不能替代产品规则确认。

## 3. 十二维检查规范

每个维度都必须给出检查结论。信息不适用时说明“不适用及理由”，不能直接删除该维度。

### 3.1 需求背景与目标

- **定义**：问题背景、业务价值、目标和成功信号。
- **检查**：是否说明为什么做、解决谁的什么问题；目标是否与具体功能区分；是否存在无法衡量的“提升体验”等表述。
- **输出**：背景、目标、成功指标；指标暂缺时标记待确认。

### 3.2 需求范围与非目标

- **定义**：本次交付包含、不包含及后续考虑的内容。
- **检查**：对象、平台、文档类型、版本和场景边界是否明确；是否容易被理解为覆盖更多范围。
- **输出**：范围、非目标、假设和分阶段边界。

### 3.3 用户角色与使用场景

- **定义**：执行者、受影响者及其典型使用情境。
- **检查**：角色是否笼统为“用户”；不同角色的目标、能力和限制是否有差异；批处理、协作或只读场景是否遗漏。
- **输出**：角色表、使用场景、角色与功能映射。

### 3.4 前置条件与触发条件

- **定义**：功能开始前必须满足的环境、对象状态和启动动作。
- **检查**：当前文档、选择集、权限、网络、依赖对象等条件是否明确；入口和触发动作是否混淆。
- **输出**：每项功能的前置条件和触发条件。

### 3.5 主流程与业务规则

- **定义**：正常路径中的操作顺序、判断条件、约束和结果。
- **检查**：步骤是否闭环；“支持”“自动”“按规则”等词是否缺少规则；批量操作的选择、预览、确认和反馈是否完整。
- **输出**：编号流程和 `BR-xxx` 规则，写明条件、动作、结果、例外及关联功能。

### 3.6 输入、输出与状态变化

- **定义**：输入数据、处理结果、对象状态和允许的状态迁移。
- **检查**：字段类型、默认值、空值、单位、精度和校验是否明确；操作前后状态是否可描述；失败时是否部分生效。
- **输出**：`DATA-xxx`、输入输出表、状态机或状态迁移表。

### 3.7 权限要求

- **定义**：查看、执行、修改、审批和管理权限。
- **检查**：谁能执行；无权限时是隐藏、禁用还是报错；跨用户、共享资源或受保护对象如何处理。
- **输出**：权限矩阵、无权限行为和审计要求。

### 3.8 异常场景与边界条件

- **定义**：失败、取消、中断、空值、极限值、特殊对象和并发变化。
- **检查**：零对象、超大数据量、只读对象、依赖缺失、重复操作、撤销失败等情况是否覆盖；错误是否可恢复。
- **输出**：异常/边界表，包含触发条件、系统行为、用户反馈、恢复方式和是否阻塞。

### 3.9 非功能要求

- **定义**：性能、安全、隐私、兼容性、可用性、可靠性和可观测性要求。
- **检查**：“快速”“稳定”“兼容”等是否有对象、负载、环境和阈值；是否确实适用于本需求。
- **输出**：`NFR-xxx`，写明适用范围、测量方法、阈值和降级策略。无业务依据时不能由 AI 自行设定数值。

### 3.10 验收标准

- **定义**：能够由产品、研发或测试验证的完成条件。
- **检查**：是否覆盖主流程、权限、异常、边界和关键非功能；是否只写“功能正常”；是否关联具体需求。
- **输出**：`AC-xxx`，使用 Given/When/Then 或等效结构，并关联 `FR/BR/DATA/NFR`。

### 3.11 PRD 与原型的关联或冲突

- **定义**：文字需求与界面、交互和状态证据之间的对应关系。
- **检查**：原型元素是否有需求依据；PRD 中的功能是否在原型体现；名称、入口、默认值、禁用状态和流程是否冲突。
- **输出**：对齐表；冲突生成 `CL-xxx`，保留双方来源，不默认任一方优先。

### 3.12 未确认事项与信息来源

- **定义**：所有未决问题、证据来源和决策链。
- **检查**：每项关键结论能否回溯；AI 建议是否被误写为事实；待确认项是否有影响、责任角色或所需证据。
- **输出**：开放问题、澄清日志、追溯矩阵和风险说明。

## 4. 问题识别与分级

| 等级 | 判定 | 示例 | 处理 |
|---|---|---|---|
| P0 阻塞 | 无法确定范围、核心规则或不可逆行为，继续会导致高概率返工 | 删除/覆盖行为、关键对象范围不明 | 单独澄清，未确认则不得标记可交付 |
| P1 高 | 显著影响主流程、权限、数据状态、异常或验收 | 批量操作是否允许处理锁定对象 | 优先单独澄清 |
| P2 中 | 影响局部交互、提示、次要边界或测试设计 | 空结果提示文案 | 可与独立问题分组澄清 |
| P3 低 | 编辑性、一致性或不改变产品行为的问题 | 术语大小写不一致 | 可直接规范化并记录 |

模糊、缺失和冲突是问题类型，不等于优先级；应结合业务影响、依赖关系、不可逆性和返工成本分级。

## 5. 编号与追溯

- `FR-xxx`：功能需求。
- `BR-xxx`：业务规则。
- `DATA-xxx`：数据、字段或状态要求。
- `NFR-xxx`：非功能要求。
- `AC-xxx`：验收标准。
- `CL-xxx`：澄清与决策记录。
- `SRC-xxx`：来源材料。

每项确定性需求至少关联一个来源或已确认的 `CL-xxx`。每项验收标准至少关联一个需求、规则、数据或非功能 ID。删除或替换 ID 时保留变更说明，避免复用旧 ID 表示新含义。

## 6. 输出质量门槛

交付前至少满足：

1. 十二维均有“已覆盖 / 待确认 / 不适用及理由”的结论；
2. P0 未决项为零，或用户明确要求带风险交付且报告中醒目标记；
3. 关键规则没有未标记的 AI 推断；
4. 功能和验收存在稳定 ID 与关联关系；
5. PRD、原型和澄清结论的冲突已处理或透明保留；
6. 六份固定输出通过确定性校验；存在原型时，每个关键 `UI-xxx` 已关联需求或明确标记“PRD未定义”。
