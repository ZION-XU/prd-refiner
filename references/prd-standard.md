# 内容规范

本文件定义分析方法和内容质量；对话节奏由入口维护，章节和字段由模板维护。

## 依据与状态

先区分输入的用途：产品要求或决定、现状证据、参考材料、AI 建议。明确适用于本期的要求可作为编写依据，仍需检查一致性及场景缺口；参考和建议须经产品采纳才能成为本期承诺。保留要求的限定条件，不因缺少外部佐证删除原稿要求。

- **已确定**：本期要求已由产品明确，或在适用的需求资料中明确且无未解决冲突；注明依据，不表示已验证可行或通过评审。
- **AI 暂定**：本稿提出的具体 AI 建议，尚未获产品采纳；说明方案、理由、适用前提和待确认部分。
- **待确认**：要求未定，本稿也未提出具体暂定方案；可列候选及取舍，说明缺什么和影响。AI 暂定与待确认均属未决，不得写成承诺；明确不适用的内容不标待确认。
- 确定性与分工分开表达：产品核对、研发评估、品质评估或共同讨论。角色可以建议，不虚构负责人、答复、日期、审核或批准。
- 同状态内容可整组标注，混合状态分别标注；确认一部分不连带确认其他内容。未决就地标记，影响范围、主要行为或结果的事项关联 DEC；已定结论写回规则，仅保留有追踪价值的取舍记录。
- 来源保留实际名称、版本／日期、位置和读取局限；仅按用户要求脱敏。同一逻辑组可共用来源。

数值要求注明依据和适用条件；性能等测量指标另说明数据规模及测量边界，实施方法可待专业评估。产品预估标“产品人员建议”，有依据的 AI 参考目标标“AI建议目标（待确认）”；采纳后更新状态并保留来源。无依据不补数值，未确认指标不作确定性验收判据。

## 从任务到规则

1. 识别谁在什么场景完成什么任务、遇到什么障碍、期望什么结果及受到哪些约束。信息少时先厘清这些要素；新增独立能力只作候选，未提及的相邻能力既不纳入本期，也不写成明确排除。用户已限定的方案作为约束；发现具体冲突时指出依据，不自行改换方案、版本或技术栈。
2. 走通代表性场景：前置条件／触发 → 操作与对象 → 产品反馈 → 状态改变或保持。只展开会实际影响结果的分支、失败、取消、恢复及边界，检查条件重叠、缺口和冲突。
3. 统一术语，删除不增加信息的重复说明；合并同一规则，拆开独立要求，保留条件、数值和例外。技术建议可入稿，但区分业务要求与待研发评估的字段、接口或算法。
4. 用“前提—动作／事件—可观察结果”的正常例子及相关反例检验规则，成稿采用模板的 Given／When／Then。验收从已明确规则推导，不新增策略或阈值；未定行为标明验收缺口。例子所需输入应明确到可选取或构造，正式测试数据和执行方案留待品质评估。

CAD 相关需求按实际影响明确对象身份、属性、关联、单位、坐标、精度、生命周期和退化／无解／多解语义；不能凭“CAD 通常如此”补定容差、默认值或对象范围。简单只读能力不凭空增加权限、并发或撤销体系。

### 模板覆盖与适用性

首次诊断完整稿任务时，逐项查看已读模板的章节、字段和示例，以具体资料和场景判断其是否影响本次需求；仍按用户任务和原文位置讨论，不按章节预先填表。模板是唯一的内容覆盖清单，字段和示例本身不是本期要求或已有答案。对相关内容记录依据与限定，区分已确定、需要产品决定、待研发／品质等专业评估及确实不适用；适用但未知不能写成“无影响”或由常识补定。产品澄清仍须满足入口规定的实质影响和责任条件，不为填满字段发问；不相关的专项不因模板列出就进入本期。

成稿前再次逐项对照模板：相关内容应有正文去向、依据与状态；未出现的内容应能判断为无关或明确未决。若此时发现新的实质产品取舍，先核对资料，再按入口规则澄清；用户要求直接出稿或明确延期时就地标未决。排版和文档元信息按模板与交付规范处理，不转成产品业务问题。

### 总体任务与故事地图

多功能、跨角色或范围取舍复杂时，按需用流程、故事地图或简短文字，不强制双图。流程说明顺序、分支、交接与完成结果；故事地图横向按用户活动／任务排列，纵向展开对应故事并说明排列依据。交付切片横贯活动且能达成用户目标，不虚构优先级或未来版本。

故事表达用户动作、条件和结果，与功能可多对多关联，不另建故事编号；单纯横排功能清单不能表达活动与故事的关系。区分已有能力、本期变更及候选，地图范围与正文一致。图示以可见排版或已渲染图像交付，不以 ASCII 或未渲染源码代替。

### 竞品与知识产权

用户要求比较，或外部比较能帮助具体产品决定时，查可核实的官方资料或演示，记录版本和来源。区分观察事实、有限样本归纳与本产品候选，说明场景是否适用，供产品取舍。资料未提及不证明产品不支持，多数产品采用不证明最佳。公共检索不发送内部需求原文；无法访问时说明限制，不编造结果。

涉及知识产权或旧稿已有相关内容时，分别保留风险分析与创新候选的依据和状态。已确认没有才填“无”，未分析填“待评估”。创新候选不等于可申请或可授权，竞品相似不等于侵权结论；专业判断留给相关角色，不阻止带明确未决的初版交付。

## 可读引用

一项规则一处完整定义，条目及引用用“名称（编号）”。功能和验收直接说明当前场景的关键约束、结果与必要判据，完整分支集中维护。引用保留必要概述和限定，不能只写“按 BR-001”。

编号按模板定义位置分配，唯一且稳定，移动或改名不重编号。旧编号不兼容或冲突时按含义转换并保留映射；历史 DATA 可转 BR、CL 可转 DEC，不机械替换。多条引用分别带名称并定位到定义，索引不是定义。

Markdown 使用目标阅读器支持的标题或显式锚点；表格单元格中可直接嵌入锚点作为跳转目标：

```markdown
[直线计数（FR-001）](#fr-001)

<a id="fr-001"></a>
### 直线计数（FR-001）

[屏幕毫米换算（BR-001）](#br-001)

| 规则名称（编号） | 适用功能及条件 | 必须发生的行为与可观察结果 | 边界、例外或保持项 |
|---|---|---|---|
| <a id="br-001"></a> 屏幕毫米换算（BR-001） | FR-001 | 换算为物理毫米 | 正实数 |
```

**严禁回音壁空小节**：禁止在表格后方建立仅有一句“见上表详细定义”、“见上表详细用例”等无实质内容的空标题小节。若条目紧凑，直接在表格单元格内嵌入 `<a id="..."></a>` 锚点；若逻辑复杂需小节展开，表格仅作清单索引，小节承载唯一完整业务规则定义。

确实不支持跳转时保留名称、编号和准确章节，并说明限制；可使用可校验的“〔直线计数（FR-001）；位置：3. 功能与交互规格〕”。检查方式见交付规范，Confluence 原生语法见平台规范，仅相应阶段读取。

## 内容复核

按实际相关场景检查，不生成固定分数或全量问卷：

- **必要性与范围**：回应真实任务，方案前提有依据；新增承诺未由例子、候选或竞品悄悄引入。
- **完整与清楚**：角色、触发、输入输出、主流程、状态、依赖及相关异常能走通；权限、非功能与产品化配套只检查实际涉及项。
- **一致**：术语、条件、数值和状态统一；未决项未在正文提前定案，真实可读的原型与文字一致。
- **可验证**：验收覆盖已明确行为及重要保持项，判据来自规则；不把验证实施问题转嫁给产品。
- **可追溯与可维护**：有效旧要求、来源、知识产权信息未丢失，引用概述与定义相符；本次范围内的规则、验收、地图和图文同步，范围外影响单独列出。

发现按“原文位置／缺失场景 → 问题及依据 → 影响 → 修改建议或待决定事项”表达，区分确定存在的问题、待核实疑点和可选建议，按影响排序。没有发现实质问题时如实说明，不为体现优化而制造问题。修改任务中，能据资料修正的在授权范围内修正，需要新产品决定的按入口澄清；只检查时报告范围与发现，不修改源稿，报告文件仅按用户要求另存。
