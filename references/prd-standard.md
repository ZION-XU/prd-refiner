# PRD 初版内容标准

本文件供 Skill 检查内容质量；唯一的 [PRD 模板](../assets/prd-template.md)维护章节、字段和简短填写提示，[工作流](workflow.md)说明交互和修改。字段清单与章节取舍直接查模板，不在此另列一套。

模板只是成稿时的固定输出容器。讨论阶段先在原始资料中提炼规则、诊断缺口并与产品经理推敲，用本文件的语义标准判断内容，不提前映射章节、补齐字段或转换编号。以下章节及编号要求在成稿时应用；明确检查结构时可提前对照模板。

## 初版与责任

初版使读者理解目标、范围、主要行为和需要继续讨论的事项。它不是审核版或可直接执行的工程承诺。产品核对、正式评审、研发完成与测试通过是不同状态。

已明确行为应有可判断结果；未知行为先记录缺口及影响，不为了填验收表编造规则。未决项可带入团队讨论；目标和主要行为尚无法理解的稿件标为待补充工作稿。

## 信息状态与依据

所有输入均作为资料参与判断，包括已有 PRD 和澄清答复；资料的名称、格式与位置不赋予其自动正确性。已有 PRD 中的方案可被诊断和重新推敲，用户当前明确约束与有效决定须尊重。来源保留不等于方案必须沿用；确需改变产品要求时展示依据、影响并取得产品决定，不静默篡改，也不以“原稿如此”为由拒绝审查。

| 内容 | 处理 |
|---|---|
| 用户明确要求、经辨明仍有效的原稿要求或明确适用本期的资料 | 作为规则分析和讨论依据，成稿时写入对应正文并保留来源；有疑点可提出修正，但不能因缺少外部佐证就擅自删除 |
| 外部参考、竞品资料、仅作背景的历史稿 | 按原名称引用，不默认继承为本期要求；先辨明资料用途 |
| 原型观察 | 只证明实际可见内容；业务语义参见原型规范 |
| AI 暂定／建议 | 可提出具体方案作为初版讨论起点，注明理由、适用前提及待确认部分；未被采纳前不写成已决定行为 |
| 冲突或未知 | 就地标明问题和影响，必要时关联开放问题 |
| 共同评估 | 标明建议参与角色、需共同决定的具体问题及影响；不要求产品先完成技术评估，也不声称相关人员已参与 |
| 不适用 | 可删除相应按需内容；不把未知当成不适用 |

保留来源名称与链接，仅在用户明确要求时脱敏。脱敏时保留可理解的代称及出处关系；不把“竞品”二字或具体商标视为自动禁止词。

确定性与讨论分工分别表达：内容可为“已确定（注明依据）”“AI 暂定（待确认）”或“待确认（尚无方案）”；另说明由产品核对、研发评估、品质评估，还是需相关角色共同讨论。提问与记录的分流遵循 [澄清方法](clarify.md)，不把专业评估转成产品必答题。建议参与角色不等于已分配负责人。影响范围或主要行为的未决项关联 DEC，同类细节可合并，不为每个字段创建问题。

字段、数据结构、接口或算法等具体建议可以写入对应章节，以帮助讨论；按条目或同一状态的整组内容标明“AI 暂定，需研发评估”，并说明哪些业务含义已确定、哪些技术细节待讨论。只有部分内容确认时分别标注，不能用整章“已确定”覆盖尚未确认的细节。AI 暂定方案不自动成为本期范围或正式验收承诺。

### 指标来源与确认状态

性能、容量及业务指标都需区分来源和确认状态：

- 资料中明确适用或产品已确认的数值，保留来源、适用场景和测量边界，可作为要求。
- 产品人员给出的预估期望标为“产品人员建议”，不把预估当作已确认阈值。
- 有讨论价值且能说明参考依据、适用前提的 AI 数值建议，标为“AI建议目标（待确认）”；标标签不能代替依据，也不授权凭经验补造数值。
- 无依据或尚无方案时保留未知，记录需评估的场景与影响，必要时关联 DEC；不强制提供 AI 参考值。

待确认指标不能写成确定性的验收通过条件。用户明确采纳后，按实际确认范围更新要求、验收与记录；研发测量可行性、品质验证方法仍按角色分工处理，不自动推定已获专业认可。

### 知识产权信息与评估边界

知识产权按模板的风险点分析与可专利点分析两部分整理，保留既有资料中的相关要求、判断依据和确认状态。框架参考用户指定的 [工作区主框架需求页面](https://confluence.zwcad.com/pages/viewpage.action?pageId=348062732)知识产权章节（本次参考页面版本 42）；该页的填写提示不构成本需求的评估结论，也不要求每次出稿重新访问该页面。

风险分析说明涉及的功能或资源、已知风险及处理要求；创新分析说明候选、拟解决的问题、已知差异与依据，可留待技术方案设计阶段进一步明确。缺少资料或未分析时标为待评估；已确认没有时才填“无”，保留判断依据。不把竞品相似、使用第三方资源或 AI 提出的创新点直接认定为侵权、无风险、可申请或可授权。

需研发、知识产权或法务等专业判断的事项记录具体问题、影响及待评估角色，重要项关联开放问题；不把专业结论转成产品必须先回答的问题，也不要求取得全部结论才交付初版。没有实际评估记录时不能虚构参与者、完成状态或审批。

## 表达与检查

模板说明信息放在哪里，下列标准判断已经写出的内容是否有用；有对应字段不等于已经满足标准。检查动作、十二个覆盖方面和角色视角见 [内容检查](review.md)，不复制为另一套填写清单。

| 标准 | 判断依据 |
|---|---|
| 必要且符合目标 | 功能回应实际用户任务；范围、例子和候选方案没有被无依据扩成承诺 |
| 清楚 | 主体、对象、条件、动作与结果含义确定；同一术语稳定，避免会改变结果的多种解释 |
| 在本期场景内完整 | 读者能走通主要任务及实际相关分支；依赖、例外与保持项足以理解，未知显式；不追求全部想象场景 |
| 一致 | 条件、数值、状态与结论不冲突；正文、验收、可读原型遵循同一决定 |
| 可验证 | 已明确行为能形成可观察结果，判断所需场景和依据可说明；没有测量依据的指标保持未决 |
| 有依据、可追溯 | 关键结论能够定位到适用资料或明确决定；引用确实支持该结论，观察、推断与已采纳决定可区分 |
| 简洁可维护 | 一项规则保留一处完整定义，引用处保留理解当前场景所需的概述；概述与定义一致，不为每句话建表或编号 |

对既有能力说明本次变化及相关保持项，不要求补全全部历史资料。图文核对读取边界见原型规范；角色视角不表示这些人员实际审核过。

## 统一框架与编号

使用模板对应字段的编号类型，不为每句建立编号。编号用于稳定定位与追踪，正文优先表达业务含义。

### 名称、概述与跳转

所有交付格式默认采用以下写法，不另维护人读版与 AI 版：

- **名称在前，编号在后。** 条目标题和表格定义项写成“直线计数（FR-001）”“计数对象范围（BR-001）”；名称简短、稳定且能区分业务含义。功能清单以名称开头，链接到功能定义；编号保持原值，改名或移动不重编号。
- **引用带名称和必要概述。** 用“仅统计选中的直线，其他对象不计入；详见计数对象范围（BR-001）”，不用“按 BR-001 处理”。关联栏可简写为“直线计数（FR-001）／计数对象范围（BR-001）”；不要求关联栏重复正文概述。
- **不跳转也能理解当前要求。** 功能说明直接交代操作、关键约束和结果；验收直接写出该场景可观察的结果和判据，不能只写“符合某规则”。完整规则集中维护；引用处允许复述必要结论、已确认阈值及适用条件，不复制全部分支和例外，不新增行为或省略会改变结论的限定条件。规则变更时同步核对引用处概述与验收。
- **名称可点击，目标有依据。** 支持文内跳转时，将“名称（编号）”链接到唯一的定义位置，不链接回索引或概述。Markdown 按目标阅读器实际支持的标题锚点或显式锚点生成链接；支持显式锚点时可用稳定编号派生的标识，如 `br-001`。表格条目无法精确定位时链接到所在小节并保留名称与编号；跳转不可用时保留名称、编号和章节位置。Confluence 按交付规范适配，不能照搬 Markdown 哈希地址。

例如，功能说明可写“用户点击计数后显示所选直线数量，其他对象不计入；详见计数对象范围（BR-001）”；验收写“选择两条直线和一个圆，点击计数，显示 2，所选对象保持不变”，并关联该功能和规则。完整的对象范围与空集处理仍在规则定义处维护。

成稿和修改后核对名称、编号、概述与目标是否对应；标题改名或位置变更后更新受影响链接。结构脚本仅检查可解析的编号定义及引用，不证明名称语义、概述一致性或实际跳转可用。

编号文本本身不会自动变成链接。Markdown 应实际生成如 `[直线计数（FR-001）](#fr-001)` 的链接，并在定义处提供目标阅读器支持的对应锚点；示例中的 `fr-001` 不能在没有目标时直接使用。打开链接的鼠标／键盘操作由阅读器及编辑模式决定，不把 Ctrl＋点击写成文稿通用要求；交付需要说明时再按实际阅读环境提示。Confluence 的链接生成和回读验证见 [条目名称与页内引用](publish-confluence.md#条目名称与页内引用)。

### 框架与稳定编号

新编、润色、深化或局部修改后的完整 PRD 均使用当前模板框架。讨论收敛或用户明确要求先出稿后，再将旧稿有效内容与本轮决定映射到相应章节，缺失内容明确标记；按需章节依模板规则取舍，不为了补齐框架编造需求。仅检查时按任务需要对照模板报告差异，不改稿。

章节内的字段和需求类别可按实际增补，模板示例不是封闭清单。产品化要求记录配套内容的新增或修改范围，不要求生成这些材料；已明确涉及但说明不全的条目保留为待补充。公司文档信息与修订记录统一放在目录前，来源放在第 9 章；原稿编审记录按所属版本保留，不在文末重复建立版本或审批表。

“编制”保留首版作者，后续实际变更人在版本修订表的“修订人”留痕。用户使用个人 PAT 调用 MCP 时，当前认证账号的真实姓名可作为修订人；采用实际账号信息或用户已提供的身份，未知则待补充。账号身份不改变产品决定的确认状态，修订人也不自动成为审核人或批准人。

按模板规定的位置定义编号。兼容模板且唯一的编号保持稳定；原编号缺失、不兼容或冲突时，分配相应编号，并在相关条目或简短修改说明中保留旧编号／原章节与新位置的对应关系，同步更新引用。结构移动不能改变产品含义，检查工具不能完整理解任意格式，应披露范围。

历史稿的 `DATA-xxx` 可按含义转为数据规则 `BR-xxx`，`CL-xxx` 的决定／未决项转为 `DEC-xxx`，来源按模板使用 `SRC-xxx`。先辨认内容再转换，不机械替换全部字符串；保留旧编号对应，不把旧编号体系带入模板作为新增要求，也不复用编号表达不同含义。

用户指定的文件或页面是本轮主要输出；未指定时通常为 `prd.md`。源稿、旧版本与同目录其他文件不自动视为冲突，也不应被删掉。实际发生澄清的编写或优化任务按 [工作流](workflow.md#澄清决策记录)配套交付澄清决策记录；其他过程附件可选，不要求附件 README 或独立追溯体系，更不能另定义一套业务规则。用户明确要求写入 Confluence 时，读取 [交付规范](publish-confluence.md)处理目标格式与原生目录；仅提供来源链接不触发写入。

本地 Markdown 默认配套保存正文实际采用的图片，并使用相对路径；来源地址另作出处记录，不能代替本地图片。获取、保存、实际查看及失败说明遵循 [图片与原型规范](prototype-analysis.md)。用户明确要求外链或指定平台输出时按其选择处理，不以脚本要求改变用户目的地。

## 检查的边界

对本地 Markdown 稿运行结构脚本时，完整初版使用 `validate_prd.py --profile template`，未完成工作稿使用 `draft`；`existing` 仅用于输入旧稿的只读诊断。远程页面或其他格式按实际内容和可用能力检查，不为脚本强制改为本地交付。脚本只查可解析结构、引用、已知模板占位及本地图片存在性，既不判断专业规则正确，也不证明已覆盖全部验收。

本地输出默认检查 `local` 图片策略，完整稿中的未本地化图片或非便携路径作为错误；工作稿保留相应提示。仅在用户明确要求外链时使用 `--image-policy external`。存在性和非空检查不证明文件能解码，更不证明图文一致。

脚本错误需修复或准确报告；提示不能当成要求用户继续作答的硬门槛。允许先保存可用工作稿。未经产品核对只能标为工作稿或初版待核对；已有文档的历史评审记录按来源保留，本轮修改不能沿用为新版本的批准结论。
