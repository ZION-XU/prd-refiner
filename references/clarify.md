# 澄清与依赖追问

在探索、编写、检查或修改中出现影响目标、范围、主要行为或验收的未知／冲突时读取。输入是相关资料、当前稿和本轮问题；结果是可回写的明确决定，或带影响说明的未决项，不是完成问卷。

## 形成值得问的问题

先查现有资料和已接受的答案，按 [内容检查](review.md)识别实际缺口。内部记录问题对应的原句／缺失位置、已有依据、影响、依赖及当前状态，不强制建立额外日志。

区分事实与决定：资料中能查到的事实先查；资料无法核实时如实说明。只有用户掌握的现状可以询问；产品取舍由产品决定，研发实现不转嫁给产品。缺少数值时可记录业务场景及期望，不能强迫给出无法证明的指标。

按影响和不确定性优先处理会改变方向或牵动多个要求的问题。措辞润色、无实际关联的边界、已确认答案不进入提问队列。明确未决并允许后续讨论的事项不反复询问。

## 提问前按责任分流

面向产品人员澄清时，先按问题需要谁的判断分流，再排列提问顺序；资料已有答案直接复用。用户主动提供专业结论时按其来源记录，不因角色分类忽略已有答案。

| 问题责任 | 处理方式 |
|---|---|
| 产品决定 | 用户场景、范围、优先级、业务规则及期望结果有缺口时，向产品澄清 |
| 研发评估 | 数据库设计、内部算法、技术可行性及实现策略不要求产品作答；记录待研发评估，可附明确标记的 AI 暂定建议 |
| 品质评估 | 测试工具、测试环境配置、样本设计和验证实施方法不要求产品作答；记录待品质评估，涉及技术条件时注明需研发参与 |
| 共同讨论 | 性能目标与可行性、验收测量口径等拆成业务期望和专业评估；只问尚缺的产品场景、可接受结果及优先级，其他部分记录待产品／研发／品质中实际相关角色共同讨论 |

产品应表现怎样、用户可接受什么结果属于产品决定，不能把全部验收问题转给品质；如何构造测试、测量和验证主要由品质与相关研发评估。目标使用环境可问产品，测试环境如何搭建不转嫁给产品。角色分工按问题含义判断，不仅按“性能”“字段”“验收”等关键词判断。

专业问题无需先询问产品“是否留待讨论”。在对应正文标注未知或 AI 暂定内容、具体讨论点、建议参与角色及影响；重要事项关联 DEC，责任人和时点未知则注明。不假装已联系或分派给相关人员，不等待这些角色答复才保存初版，也不在后续轮次把已留待专业评估的问题重新问给产品。

## 按决定的依赖推进

将问题组织成简短的依赖关系：哪些决定已经成立，哪些问题必须等待上游答案。共同优化默认每轮只问一个当前最重要、前提已明确的产品问题；只有用户希望批量回答时，才将 2～3 个互不依赖的小问题成组。完整问题队列内部维护，不把整棵问题树一次交给用户。

用户回答后重新判断：哪些问题已得到答案，哪些分支已不适用，哪些下游问题现在才有必要。不要继续执行过时的固定问卷，也不从答案中扩大出未经同意的新功能。

例如批量操作中，“部分对象失败时是否保留成功项”会影响“撤销应恢复哪些对象”。先确定前者，再具体化后者；不能在同轮把尚未确定的失败策略当成撤销问题的前提。

## 交互方式

当宿主提供原生结构化选择/自定义输入控件，且当前模式允许调用时，优先用控件提出本轮澄清。默认一次调用只提出一个问题；用户希望批量回答时，才将 2～3 个互不依赖的小问题放入同一次调用。控件选项只用于真实互斥候选：材料足以支持推荐时将推荐项排第一并说明取舍；没有依据时不要伪造推荐或默认答案。

控件不可用、当前模式不支持、用户正在快速口头澄清，或问题需要开放描述而非候选选择时，降级为普通对话；保持相同的问题数量和等待规则。说明缺口和影响，接受编号、自然语言或“暂不决定”。不要声称已经使用了宿主控件，也不要求用户为澄清切换模式。

提出问题后等待真实回答：普通对话在问题后结束本轮，不紧接着生成 PRD；异步控件返回仅表示问题已展示，默认选项也不表示用户已选择。不能用自行选择建议、超时或把问题写为“待确认”来代替回答并继续出稿。共同优化的首轮只给简短理解与一个关键问题，不附完整检查报告或全部未决项；用户主动要求查看完整清单时可展示，但展示不等于完成澄清。

## 苏格拉底式提问的使用

为一个实际问题选择有用的问法，不轮流套完全部类型，不用连续反问迫使用户接受建议：

| 目的 | 问法示例与适用条件 |
|---|---|
| 澄清概念 | “这里的‘相同设备’按什么区分？能用一个实例说明吗？”用于会改变识别结果的歧义 |
| 检查假设 | “这个场景是否保证图块都有该属性？如果没有，期望怎样处理？”用于有实际可能性的隐藏前提 |
| 找依据 | “这个数量上限来自现有规则、实际图纸还是暂定目标？”资料中找不到时才问 |
| 比较路径 | “如果只提供手动刷新，是否已经解决当前任务？哪些情况必须自动更新？”用于尚未确定的方案 |
| 检验后果／反例 | “结果生成后源对象被删除，用户应看到什么？”仅用于本次确有持续关联的结果 |
| 收敛问题 | “这项选择会影响初版的主要行为，还是可以保留给后续讨论？”用于判断是否值得继续 |

每个问题带必要背景和影响，使用户不用理解内部方法即可回答。有真实候选时说明取舍及建议依据，允许自由回答；没有依据不伪造选项、推荐或默认答案。简短不等于把回答限制为几个字；不用固定追问次数。

## 接受、回写与停止

明确回答后更新对应要求以及受影响的流程、验收和图文，删除被替代的矛盾表述；保留简短决定依据，必要时在模板的开放问题位置记录。实际发生澄清的编写或优化任务，交稿时按 [澄清决策记录要求](workflow.md#澄清决策记录)另附真实交互记录；不为记录提前出稿或补造讨论。文件保存遵循工作流，只检查任务不改源稿。答复有歧义且会改变行为时，先核对理解，不能自行补全。

资料充分且用户明确要求直接交稿时可零提问。共同优化即使没有业务缺口，也先依据资料提出具体优化方向供用户选择，不编造缺口。目标、范围、主要场景、规则和可观察结果经过推敲，关键冲突已解决或明确延期时，才进入成稿；不能把回答第一题当成完成全部讨论。用户明确停止追问／先出稿时可提前输出。某一题的“暂不决定”只延期该项，其余独立关键问题仍按需推进。核心尚无法理解时标为工作稿。深度追问服务共同理解，不要求穷尽每个分支或解决所有工程问题。
