# 交互与原型设计

仅在需要把单个 FR 细化到“可开工”时读取：设计交互、出帧、确认后增量写入正文第 3 章。

## 一、为什么交互细节必须借原型与状态推出来

桌面 CAD 的多数决策不是参数选择，而是离散的“状态 × 事件”组合：拖动时橡皮筋画什么、捕捉与正交冲突时谁优先、第 3 步按 ESC 是整体回滚还是保留已完成段、空选区点击后是静默还是提示、退化几何出现在命令行哪一行。这层设计只在“走一遍状态”时才暴露缺口，靠文字段落推不出来。

三件套分工，任何一件缺席都会让细节在成稿时缩水：

| 载体 | 证明什么 | 不证明什么 |
|---|---|---|
| 帧（画面） | 布局、控件、文案、默认值、显隐与可用态、提示行内容 | 迁移逻辑、异常路径、数据约束 |
| 状态事件表 | 进入条件、每个事件的反馈、迁移、取消与回滚、撤销分组 | 视觉细节、业务规则依据 |
| 正文条目 | 看不见的行为契约：命令别名、系统变量、精度单位、兼容、性能、异常语义 | 画面布局（只引用帧，不重复描画） |

单源规则：同一行为只允许一处完整定义（见 [内容约定](prd-standard.md) §3），帧与正文互相引用而不互相抄写。

## 二、逐 FR 小循环（不要等整稿）

一次只做一个 FR，确认一段写一段；成稿阶段只做装配与一致性，不重新发明细节。

1. 写一句意图与前置：谁、在什么状态下、要得到什么结果。
2. 先列状态与事件（可以还没有画面），把“进入—操作—反馈—退出”的骨架摊开。
3. 画最小帧集。
4. 对着帧回填状态表：每个状态被操作时屏幕上发生什么；写不清的地方就是缺帧或缺状态。
5. 找异常与退出：空选区、无效或退化几何、只读／锁定／冻结、跨文档、ESC、撤销重做。
6. 请用户看图确认（看图的拍板成本远低于读一段文字），确认后立即增量写入主稿第 3 章。
7. 进入下一个 FR。

帧或状态表改动后必须回写正文；不允许“图改了正文没改”，也不允许“正文改了图没改”。

## 三、交互卡结构（正文承载）

交互规格卡（简称交互卡）负责承载功能的完整交互闭环，支持两种形态（优先推荐形态一）：

### 1. 首推形态：以原型图为中心的状态走查卡（人机双友好）

适用于绝大多数包含图形界面、对话框或视口交互的功能。解决传统大段文字堆叠导致评审认知过载、图文脱节的问题：

- **状态原型图置顶**：按操作流转划分状态小节（如 `#### 状态一：设置对话框（FR-001-S1 初始态）`），原型图直接置顶呈现，作为第一视觉锚点。图名包含帧 ID。
- **标号走查（Numbered Callouts）**：在 Figma 原型或设计图的关键控件上标注清晰的数字标号（1、2、3...）。正文紧随其后以 **“界面要素与操作说明”** 顺着标号对号入座：
  - 标号 + 控件名称（控件类型）；
  - 初始默认值、取值范围或选项枚举；
  - 用户操作、即时界面变化与命令行回显（可观测事实）；
  - 界面联动效果与下一状态迁移。
  - 人类在评审时顺着图上标号与说明即可 3 分钟通读整个界面，无需脑内人肉渲染。
- **业务规则与异常处理（不可见契约伴生）**：紧随界面说明之后，将只有文字能表达的深层逻辑清晰分列：
  - **系统变量与配置**：双向绑定的系统变量（如 `CTABLESTYLE`）、配置项与作用域；
  - **输入约束与校验**：数值范围、非法字符拦截与失焦恢复机制；
  - **视口后续与数据契约**：点击确定后的视口提示流（如 `指定插入点: `）、图元生成或数据持久化契约；
  - **取消、中断与撤销**：按 `ESC` 键或取消按钮的可见状态与数据回滚，以及 Undo/Redo 撤销分组。
  - 研发与 AI 拆分任务时可直接消费此块契约，无缝落地代码与测试用例。

### 2. 备选形态：经典表格型交互卡

适用于纯命令行提示流、无复杂界面的轻量改动或后台逻辑衍生交互：
- 结构包含：入口与前置、取消与回滚、命令行等价、状态与事件表（表头含“状态”“可见反馈”，至少两行）、帧清单表格（表头含“帧 ID”“画面”，至少一行含 `FR-xxx-Sx`）。

### 3. 核心准则（两种形态通用）

- **六要素守恒**：入口与前置、帧清单（或内嵌帧图）、状态与事件说明、取消与回滚、系统变量/命令行等价、待确认项。
- **最小帧集**：默认态、输入或预览态、完成态、异常态、取消后态。按功能增减，缺帧必须写明原因（登记 DEC 或说明不可出图），不得静默省略。
- **状态说明原则**：反馈必须写可观察事实：“命令行回显‘已选择 3 个对象’”“计数按钮由灰变亮”，严禁写“提示用户”“反馈友好”等主观虚词。
- **异常与取消先行**：先定 ESC／取消后的可见状态与数据状态，再补成功路径。先写正常路径的习惯会系统性漏掉回滚与残留。

## 四、帧清单与 `manifest.json`

机器可查的帧清单固定落 `.assets/frames/manifest.json`，与正文帧表一一对应：

```json
{
  "requirement": "<需求名>",
  "frames": [
    {
      "id": "FR-001-S1",
      "fr": "FR-001",
      "state": "S1 默认态",
      "image": ".assets/images/fr-001-s1.png",
      "source": "figma:<文件>:<节点> 或 excalidraw:<文件名>",
      "version": "0.1",
      "captured": "YYYY-MM-DD",
      "note": "约束范围"
    }
  ]
}
```

- 必填：`id`、`fr`、`state`、`image`；`source`、`version`、`captured`、`note` 按需。
- `id` 用 `FR-<功能号>-S<状态号>`，与正文帧表、帧图文件名一致（`fr-001-s1.png`）。
- 帧图稳定命名、重出即覆盖；manifest 记版本与截取日期，用于回溯“这版稿对应哪版界面”。
- 帧图与可编辑源文件都落 `.assets/`（图片进 `.assets/images/`），正文只引本地图片，源文件不进正文（见 [成稿与交付](delivery.md)）。

## 五、工具链：先探测，再声明，最后降级

不写死任何原型工具的能力——MCP 服务的读写范围与版本相关，随接通情况变化。每次进入交互设计先做一次能力探测，并声明本次路径：

1. 当前可用的原型 MCP 能做什么：读帧、导出图、写帧／注释分别判断，不假设“连上就等于能写”；
2. 改动发生在哪一侧：AI 直接写帧，还是用户在设计工具里画、AI 读回；
3. 本轮能否导出本地图片：不能导出就只能引原型链接，并登记“图未落盘”的影响。

降级链（从上往下选，选了哪层必须写在交付说明里）：

1. 原型工具 MCP：可读帧并导出本地图片；
2. 可编辑场景文件（`.excalidraw`，生成方式见 [可编辑图表](visual-collab.md)）；
3. 状态图 + 文字状态表（Mermaid 或结构化步骤）；
4. 纯文字状态表，并显式声明“未出图”、登记 DEC；不得把文字表冒充已出帧。

MCP 只读时：用户在设计工具里改，AI 每次改动后重新读回并比对正文，禁止凭记忆推断画面上有什么。
MCP 可写时：AI 写入的帧仍须用户确认，“我能改”不等于“已确认”。

## 六、视口类动态反馈怎么表达

橡皮筋、捕捉／追踪提示、预览几何、grip 编辑这类视口内动态反馈不适合由单张静态帧承载，用“帧序列 + 标注”表达：

- 同一状态出多帧（起始、拖动中、吸附后），每帧标注鼠标位置、光标形状、提示行内容、预览几何；
- 状态表把这些标注写成可观测反馈，不写“实时预览”；
- 只能用连续动画表达的反馈，写明“逐帧无法证明”，并登记 DEC 由研发定实现判据。

## 七、与门禁和校验的关系

- 交互稿的逐 FR 确认记 `ux` 门禁（判据见 [需求探索](brainstorm.md)），确认后正文增量生长。
- 交互卡完备性与图文一致性属 PRD 内容规则，归 [内容约定](prd-standard.md) §5；此处只给方法与产物契约。
- `scripts/validate_prd.py` 检查交互卡结构并输出覆盖率，`scripts/validate_frames.py` 检查正文与 `manifest.json` 的双向闭包。
- review 阶段的交互视角是兜底，不是设计发生的地方（见 [下游审查](downstream-review.md)）。

## 八、反模式

- 先写完整文字稿，最后“配几张图”：图退化成插图，交互决策依然没做。
- 一帧走天下：只有完成态，没有预览态、异常态、取消后态。
- 帧上改了布局，正文控件名与验收没改。
- 把原型工具的注释当规范：注释会随文件散佚，规范必须落在正文。
- 用截图替代原型：截图只证明“现在是怎样”，不证明“应当是那样”（证明边界见 [原型分析](prototype-analysis.md)）。
