# 面向需求决定的竞品分析

仅在用户要求，或存在可通过外部事实帮助解决的具体产品问题时读取。不把竞品研究设成每份 PRD 的前置条件；目标是支持当前决定，不扩展成市场报告。

## 确定比较问题与证据

先写清要回答的问题，例如“相似任务如何让用户核对批量操作结果”，而不是罗列竞品所有功能。选能说明不同处理方式的少量可比产品或资料；已有证据足够支持决定时停止扩展。

使用用户提供的资料，或宿主实际可用的搜索、网页、文件和图像工具。验证会变化的产品行为时优先读取官方帮助、产品文档、版本说明或可核实演示；搜索摘要不能代替原文。图像的观察边界遵循 [原型规范](prototype-analysis.md)。无访问能力时说明限制，用现有资料继续，不能凭记忆编造竞品行为或来源。

保留实际产品名称、版本或资料日期、链接／文件位置与读取限制。不要把内部需求全文或专有信息复制到公共搜索查询，使用完成查询所需的通用任务描述。名称仅按用户明确要求脱敏。

## 归纳可比行为

围绕同一任务比较输入、操作、结果反馈、错误恢复及限制中实际相关的部分。将结论拆成三层，不能跨层冒充：

| 层次 | 应记录什么 |
|---|---|
| 观察事实 | 哪份资料支持什么行为，适用的产品版本／条件是什么 |
| 归纳解释 | 有哪些共同点、差异或反例；由哪些有限样本推得，有什么不能确认 |
| 本产品候选 | 哪种做法可能满足当前目标，需要哪些前提，代价或限制是什么 |

一份资料只能支持该资料范围内的观察，不能称为行业惯例；未写某行为不证明产品不支持。营销描述不能证明具体异常策略，样本多数也不证明最佳方案。冲突资料保留出处和版本差异。

## 回到本产品作决定

用 [需求探索](discover.md)中的目标与基本约束检验候选：用户、对象、任务频率、既有操作和失败代价是否可比？必要时保留更简单的候选或解释不采用的理由。

只把用户明确采用且有适用依据的决定转入正文要求；未经选择的方案标为建议或未决。不能照搬竞品默认数值、专业语义或性能承诺。PRD 的来源位置保留实际依据；比较细节只在有必要或用户要求时另存，不强制生成独立报告。
