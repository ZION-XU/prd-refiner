# 需求内容检查

在只检查任务、编写前识别缺口、实质修改后及交付前读取。开始检查前必须读取 [内容标准](prd-standard.md)，当前上下文已有完整内容时复用。模板只负责内容位置。检查文稿是否表达清楚，不测试软件是否实现，也不生成总分或固定评分报告。

讨论前的诊断直接针对原始资料，按场景走通规则、寻找矛盾与缺失前提；不先映射模板，也不把模板字段空缺直接当成产品必答题。诊断结果用于选择当前最值得推敲的问题，默认内部维护完整发现，只向用户呈现本轮焦点及必要依据。

已有 PRD 与 AI 生成过的草稿同样接受诊断。先检查方案是否回应真实任务、前提是否成立、是否有被现有写法遮蔽的替代方案；不能只在原方案中补字段、补异常。发现根本问题时提出依据与重构方向，与产品经理推敲后再组织成稿。用户限定局部修改时，在范围内执行，范围外发现仅提示。

## 从证据发现问题

先确定本轮目标、文稿版本、可用资料与修改范围。通读主要场景，建立必要的“目标—行为—规则—验收—来源”对应；按业务含义核对，不能只凭关键词或编号相同认定一致。

对已写内容找多种解释、缺少前提、无依据数值、近义重复或明确矛盾；对缺失内容，说明哪个实际场景因此无法理解或判断。没有材料证明的疑点列为待核实，不断言业务错误。明确未决项可记录为遗留缺口，不等同于未表达或阻止出稿。

## 按需覆盖的十二个方面

以下是问题扫描范围，不是额外章节、十二轮问卷或十二项得分。已有明确答案直接引用；无关方面跳过，无法读取的依据如实注明。不要与角色视角作全量笛卡尔组合。

| 方面 | 具体检查动作 |
|---|---|
| 背景与目标 | 功能是否回应已说明的用户问题，目标是否只是重复方案名；成功含义能否解释 |
| 范围与非目标 | 本期承诺与排除项是否冲突，例子或后续想法是否被扩成当前要求 |
| 角色与场景 | 任务由谁在什么情境完成，角色差异是否实际影响行为，场景能否走通 |
| 前置与触发 | 开始条件和触发是否明确，流程是否隐含尚未满足的条件 |
| 主流程与业务规则 | 关键步骤是否有结果，条件分支有无冲突或缺口，同一规则是否多处不一致 |
| 输入输出与状态变化 | 对象、输入约束、输出含义和保持项是否清楚；相关状态变化是否有因果依据 |
| 权限 | 仅在存在角色、授权或受限操作时，核对谁能做什么及限制后的行为；不凭空创建权限体系 |
| 异常与边界 | 针对实际输入和状态变化找反例；失败、取消、部分结果或恢复是否影响本期行为 |
| 非功能与产品化要求 | 相关质量约束有无场景与判断依据，数值是否有来源，未知是否被经验默认替代；按实际影响核对配套内容，类别由产品增减，已明确涉及但细节未定的要求不能丢失 |
| 验收标准 | 能否从已明确规则得到可观察结果；是否漏掉关键行为，或在验收中新增规则 |
| PRD 与原型 | 实际可读图文的入口、状态、反馈等是否一致；无原型不算缺陷，未读取不能称已一致 |
| 来源与未决事项 | 证据是否真的支持描述，竞品观察是否被写为承诺，未决项是否在正文中被当成定论 |

## 用角色视角补充检查

根据实际影响补充查看，共享同一问题清单并合并重复发现，不模拟多名人员已完成评审：

| 视角 | 重点动作 | 可产出的发现 |
|---|---|---|
| 产品 | 从目标反查功能必要性、本期范围与方案取舍 | 偏离目标、额外承诺、方案假设未确认 |
| 研发 | 逐场景推演对象、状态、联动及失败结果，指出必须猜测的行为；不替研发选算法 | 条件缺失、状态矛盾、依赖或兼容含义不明 |
| 品质 | 试构造正常和相关反例，将预期逐项对照规则与来源 | 结果不可判定、关键保持项遗漏、验收越过规则 |
| 产品设计 | 按真实操作顺序核对可发现性、反馈、恢复及图文一致性 | 操作断点、状态反馈缺失、原型与文字冲突 |

## 发现、处理与复查

新编或实质优化稿交付前，做以下交叉核对；在现有正文中修正，不另建固定报告：

- 从“本期包含”逐项反查输入依据。新增独立能力若仅有 AI 建议，移为明确候选；不要用“整份初版待核对”掩盖未经采纳的范围承诺。对用户原稿已有但依据不明的要求先提示核对，不擅自删除。
- 从每个未决项反查相关正文及验收，检查是否提前选定方案；从每个“已确认”反查实际答复。仅有当前提示词时不能声称发生过额外确认轮次。
- 核对拟提问题是否按澄清规范分流：研发实现、品质验证方法留为专业讨论点；共同议题仅询问产品能决定的部分。预期产品结果仍须明确，不能因涉及验收就全部留给品质，也不以等待专业结论为出稿门槛。
- 将验收的条件、分类、阈值和结果逐项对照规则。例如“每次不超过阈值”与“95% 不超过阈值”不等价；验收不得新增前置条件。方案尚未选定时，验收只能覆盖共有的已知行为，方案特有的结果需标明适用条件或验收缺口。
- 核对交付正文是否残留模板填写说明、占位行和标题标记，包括【核心】、【按需】、【多功能时填写】。结构脚本通过不代表这些检查已完成。
- 按内容标准的“名称、概述与跳转”检查阅读连续性：不点击引用能否理解当前操作和预期结果，关联是否带名称，概述是否保留必要限定并与完整规则一致；执行下方交付检查核对引用目标。静态链接检查不能证明实际跳转或语义一致性。
- 总体表达核对起点、交接、完成结果及与单功能正文的对应，不强制双图。故事地图检查：横向能否讲通用户过程，故事是否对应上方任务，纵向依据是否明确，交付切片能否达成其目标，范围与优先级是否有依据。分栏或卡片数量不能证明二维关系；已有能力和候选不能变成新增承诺。
- 涉及知识产权时分别检查风险点分析与创新候选，核对依据和评估状态；“无”是否有依据，待评估是否被写成已确认结论。保留原稿有效信息，专业判断按责任分工记录，不以补齐栏目为由虚构结论。

输出有行动价值的发现：**原文位置／原句或缺失场景 → 问题及证据 → 影响 → 建议修改或待确认问题**。标明属于已证实冲突、待核实缺口还是可选建议；按对方向和主要行为的影响排序，不以数量证明检查质量。

模糊、遗漏、冲突是问题类型，不直接等于严重程度。结合影响范围、决定依赖、不可逆结果及返工代价排序；优先澄清会改变核心对象、范围、删除／覆盖等结果的问题。低影响表达问题可在授权范围内直接规范化，不要求用户逐项批准。核心未决决定稿件状态，不能据此拒绝保存已知内容。

仅检查时报告发现及实际检查范围，不改源稿。编写／优化时，已有资料足以决定的修正直接回写；需要产品决定的交给 [澄清](clarify.md)，允许保留明确未决。修改后复查受影响的规则、验收、图文及保持项，移除已经失效的问题，避免反复报告同一已解决事项。

检查结果可以简短交付；用户要求时才另存报告。结论只覆盖实际查看的资料和范围，不把“未发现问题”写成“完整、正确或正式评审通过”。

## 交付检查

完整稿交付前扫描全部当前条目引用：识别定义、索引和引用；定义采用名称（编号），引用的名称与编号须对应同一完整定义，目标存在且唯一。检查范围、功能清单、正文、流程及验收关联，多个编号分别链接。历史编号、外部资料中的编号和代码示例不强制指向当前定义。名称语义、概述一致性及无法解析的格式需人工核对。

有本地 Markdown 稿及 Python 能力时运行两项只读检查（路径相对 Skill 根目录）：

```text
python scripts/validate_prd.py <稿件路径> --profile template
python scripts/validate_links.py <稿件路径> --format markdown --profile template
```

`validate_prd.py` 检查模板结构、编号定义及引用、已知占位和图片路径；`validate_links.py` 单独检查命名形式、条目引用链接、锚点唯一性及对应定义。完整新稿或优化稿使用 `template`；未完成工作稿用 `draft`；输入旧稿诊断用 `existing`，不能用它判定新稿合格。链接问题在 `draft`／`existing` 中作为提示，完整稿作为错误。

Markdown 链接检查支持本规范的显式锚点、GFM 常规标题锚点及行内／引用式链接；其他阅读器、复杂 Markdown 或跨页目标需按结果提示核对。无法可靠跳转时按内容标准保留名称、编号、章节并说明限制，不伪造通过，也不为通过检查删去必要引用。

图片策略默认 `local`：完整稿中远程／内嵌数据图片、非便携路径或缺失文件不通过；`draft` 提示未完成本地化。仅用户明确保留外链时使用 `validate_prd.py --image-policy external`；`existing` 默认诊断外链。脚本不下载图片、不验证像素，不代替实际查看。

Confluence 完整稿必须对准备提交以及回读的 Storage 分别运行组合检查（使用实际绝对路径）：

```text
python scripts/validate_delivery.py <Storage文件> --workspace <用户工作区根目录> --markdown <实际交付的Markdown文件>
```

该检查同时执行 Markdown 结构、图片及引用检查，核对 Storage 引用目标、两份文稿当前定义编号集合，以及中望目录方案的文首右侧原生格、包裹整个 expand/toc 的浮动容器和后续 single 全宽正文；拒绝依赖内联定位的旧结构。站点 CSS 是否生效需另行核对。默认要求 Markdown 直接位于工作区根目录，隐藏 Artifact、临时 XML 不算交付。用户明确指定其他文件夹时加 `--output-dir <目录>`；明确不要本地稿时才用 `--remote-only` 并省略 `--markdown`；明确采用正文目录时才用 `--layout inline`。外链图片例外使用 `--image-policy external`。这些参数记录真实用户选择，不能为绕过错误自行使用。

完整稿检查失败先修复再发布；无法运行时保留工作稿并报告未检查，不能宣称交付合格。局部修改可保留授权范围外的旧问题，但须区分本轮变更检查与全页检查结果，不扩大修改范围。临时 Storage 只用于准备和回读核对，不代替本地 PRD。组合检查没有网页渲染能力；它通过后仍须按平台规范核对实际点击、折叠、浮动和两份正文一致性。

组合检查同时报告 Storage 中的 `code`／`noformat` 宏；默认完整交付不使用它们。原型、故事地图和流程应显示为实际排版或图像，不能仅提供代码源文；删除宏时须保留其必要内容，不以漏图换取检查通过。

已发现的问题在授权范围内修复并复查；只检查任务仅报告。脚本不可用、格式超出支持范围或无法查看目标时说明缺口，不以跳过检查报告成功。脚本不自评内容分数、不读取同目录其他文稿、不改变用户目的地。最终保存和状态按 [工作流](workflow.md)处理。
