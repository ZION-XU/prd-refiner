# 编写、检查与修改工作流

任务路由与进入成稿的条件由 [Skill 入口](../SKILL.md)维护。本方法负责资料整理、局部修改、多轮接续及保存交付；不因读取本方法就提前出稿。

## 资料定位与读写

目录输入先查相关文件，区分当前稿、参考、历史和重复材料，不读取无关配置、凭据、缓存或第三方实现。资料很多不等于已经充分。文件无法定位时不要选取另一项目的稿件代替。

来源与输出目的地由用户决定。用户指定通过 MCP 读取时，用宿主实际可用工具取得资料，记录来源、版本和读取限制；指定写入时在内容准备好后按其要求输出。Skill 不自行禁止或强制使用 MCP，也不把 MCP 读写设计成另一套需求优化阶段。没有所需能力时如实说明，不能根据页面编号臆造内容或虚报写入成功。

## 整理任意格式资料

以内容含义提取信息，不把原文标题和表格当作完整性证明。一个段落可能包含多个独立要求；分散在多处的同一规则可合并，保留相关出处和限定条件。先识别事实、当前要求、参考、建议及未知，沿业务场景提炼规则、审查并讨论，不按模板槽位整理问题；成稿时再映射到模板。详见 [内容标准](prd-standard.md)。

需求、旧 PRD、原型、聊天回答及后续反馈统一作为资料，不把“已有 PRD”当成只能局部修补的成稿。先判断其中哪些是有效要求、哪些只是历史方案或假设，再检查目标与方案是否一致；需要时提出重构、替换或删除建议，并由产品决定业务取舍。明确限定的局部修改仍守住范围，不能借此重做其他功能。

为实际使用的来源保留名称、版本或日期、位置及读取限制；同一逻辑组可共用来源，不强制每句话建立台账。不能把来源数量或文件格式当作可信度。

内容展开用 [细化方法](specify.md)，发现疑点用 [检查方法](review.md)，需要产品决定时用 [澄清方法](clarify.md)。用户明确变更旧规则时执行并同步关联内容；冲突优先关系不明时保留双方出处。历史依据可以留在来源或版本记录中，当前正文不并列互相矛盾的有效规则。

## 局部修改

1. 读取内容标准、当前稿及本次要求，按原文位置定位受影响的场景与规则，保留图片、来源和历史记录；不先重排全文或转换编号。
2. 在约定范围内修改内容。仅润色时比较行为含义；规则变更时同步引用处的名称、概述和验收判据。不能用框架迁移作为新增产品决定的理由；范围外需要联动的内容明确提示，不擅自扩大修改范围。
3. 核对未受影响的目标、范围、数值和规则含义是否保持，改名、移动或必要编号转换后的链接是否仍定位到定义。对不能核实的原稿内容提示问题，不擅自删掉。
4. 输出完整稿时读取模板，将优化后的有效内容映射到对应位置，处理必要编号转换；已符合模板的稿件保持框架。默认另存结果，保留源稿；用户明确要求更新指定文件时执行。重名时用新版本名，不覆盖其他文件。
5. 分别说明模板结构调整和实际内容变更，必要时显示差异。结构检查使用 `template` 或 `draft`，不以输入旧稿的 `existing` 检查替代。

## 多轮与继续

当前文稿保留目标、范围、已明确规则、版本及未决内容，使后续轮次不依赖无限聊天历史。未发生澄清的简单修改无须额外生成过程文件。

共同优化尚未成稿时，用已有来源和当前对话维护已答决定及剩余问题；无需为了记录进度提前生成整份 PRD。每轮收到回答后先简短说明其影响，必要时展示对应段落，再提出下一个必要问题并等待。成稿时将决定写入对应内容，不能只保留在聊天中。

继续任务时读取当前资料和最新稿，汇合可读的决定与新反馈，再诊断本次问题；不把继续任务固定为在上一份初稿上修补。新会话由用户提供当前资料，不承诺自动恢复历史对话。若意外读到旧版而无法判断，以用户指定版本为准或说明冲突。

### 澄清决策记录

实际发生澄清的编写或优化任务，在收敛交付或用户要求提前出稿时，将真实交互提炼为独立记录，与 PRD 一并交付。未发生澄清的直接出稿、简单润色和仅检查不强制生成；用户明确不要记录时遵循其要求。讨论期间维护已有回答与未决，不要求每轮另存文件或提前生成完整 PRD。

记录包含关联 PRD 及版本、问题与背景、实际提出的候选及简要取舍依据、用户回答或明确未决状态，以及落入主稿的位置或已有编号。只记录可读取的真实讨论，不补造未提出的选项、回答、轮次或确认人；没有候选时直接记问题与回答。分析依据采用可核对的简要理由，不要求复述模型内部推演。回答改变时保留必要的替代关系，当前有效要求以 PRD 为准。

本地默认使用 `<需求名>_澄清决策记录.md`，与主稿同目录，沿用同一任务已有记录。Confluence 交付也默认配套本地记录；用户明确仅远程时遵循其选择，可使用该目的地下用户授权的独立附件或记录页面。不因主稿写入获准而自行创建范围外页面；工具无法交付记录时说明缺口并提供可复制内容。记录引用正文，正文保留必要决定依据与未决影响，重要项关联第 8 章；不把全部已解决过程复制到第 8 章，也不维护第二套业务规则。

## 保存、状态与失败

本地 Markdown 成稿前，按 [图片与原型规范](prototype-analysis.md)自动下载／导出并归集正文采用的图片到文稿旁的资源目录，改用相对路径；来源类型不改变此要求，无须用户另行提醒。核对真实文件、图像可读性和引用。取得资料时即可保存相关图像供分析，不必为保存图片提前生成 PRD；无法取得的图片作为明确交付缺口保留，不能把远程链接当成本地化成功。

| 交付状态 | 条件 |
|---|---|
| 待补充工作稿 | 目标、范围或主要行为仍不足以理解，交付已知内容与缺口 |
| 初版待核对 | 目标、范围及主要行为可理解；已知规则入文，未决与限制显式，完成本轮检查，待产品核对 |
| 可供团队讨论的初版 | 产品人员已认可本轮稿件可用于团队讨论，允许保留共同判断事项 |

不因脚本通过自动升级状态；任何状态都不等于正式评审、开发批准或测试通过，也不要求问题清零或研发签字。历史审核记录按所属版本保留，不沿用为本轮批准结论。

主要交付一份可编辑 PRD；未指定时在当前用户工作区根目录保存 `<需求名>.md`，需求名未定时用 `prd.md`，重名时另取版本名。用户指定其他输出目录时遵循其选择。Confluence 发布默认同时交付该本地 Markdown，发布前必须实际写入并回读文件；隐藏目录、内部 Artifact、临时 Storage 和聊天代码块不算本地 PRD。用户明确“仅远程／不要本地文件”时才省略本地稿；没有工作区或无法落盘时说明缺口，不能悄悄改为仅远程并宣称完成。本地与平台是同一需求的两种格式，核对正文、版本及条目一致，不另维护两套规则。

默认另存并保留原稿；明确要求更新指定文件时执行。局部修改 Confluence 时，以保留范围外内容的合并结果形成本地镜像，不能将镜像反向转换后覆盖整页。澄清记录按上节触发，其他材料按需，不强制另建交互规格、追溯矩阵、评分卡或附件 README。编制与本次修订人按内容标准记录。

本地 Markdown 保存后执行交付检查；Confluence 的最终正文必须按 [交付规范](publish-confluence.md)准备、检查并以 Storage 提交，已有转换能力可用于准备，但转换结果不自动合格。工具的 `content_file` 可能指 MCP 服务端文件系统，不能假定它能读取用户工作区；未核实共享路径时使用正文参数。脚本不可用、附件未读取或保存／写入失败时说明实际未完成部分，不能报告不存在的文件、页面或未运行的检查。交付时分别给出本地文件链接、远程页面链接和实际检查结果；内容质量、落盘、写入与渲染分别判断。
