# 编写、检查与修改工作流

## 路由和信息缺口

首先识别本次任务。编写和优化统一使用 PRD 模板；框架迁移与内容修改分开处理，不能因迁移而改写未受影响的要求：

| 情况 | 下一步 |
|---|---|
| 资料充分，明确要新稿 | 按模板生成初版待核对，无须先问问题 |
| 想法很少，目标或主要行为不明 | 用 [需求探索](discover.md)明确任务、约束与方向，不直接按章节填空；用户希望先出稿则标为待补充工作稿 |
| 已有稿，只检查 | 对照模板与内容标准给出位置、证据与影响，不修改源稿，也不要求把检查结果落成 PRD |
| 已有稿，只润色 | 按 PRD 模板组织，保留范围、规则、条件和数值，精简文字，不新增产品决定 |
| 已有稿，要求深化或修改 | 按 PRD 模板组织，明确内容修改范围，补充资料已支持的内容；必要产品决定再澄清 |
| 用户暂停、跳过或先出稿 | 保留已知内容和未决影响，结束本轮；不因问题没答完持续追问 |

目录输入先查相关文件，区分当前稿、参考、历史和重复材料，不读取无关配置、凭据、缓存或第三方实现。资料很多不等于已经充分。文件无法定位时不要选取另一项目的稿件代替。

## 整理任意格式资料

以内容含义提取信息，不把原文标题和表格当作完整性证明。一个段落可能包含多个独立要求；分散在多处的同一规则可合并，保留相关出处和限定条件。先识别事实、当前要求、参考、建议及未知，再映射到模板；详见 [内容标准](prd-standard.md)。

为实际使用的来源保留名称、版本或日期、位置及读取限制；同一逻辑组可共用来源，不强制每句话建立台账。不能把来源数量或文件格式当作可信度。

内容展开用 [细化方法](specify.md)，发现疑点用 [检查方法](review.md)，需要产品决定时用 [澄清方法](clarify.md)。用户明确变更旧规则时执行并同步关联内容；冲突优先关系不明时保留双方出处。历史依据可以留在来源或版本记录中，当前正文不并列互相矛盾的有效规则。

## 局部修改

1. 读取当前模板、内容标准、当前稿及本次要求。旧稿先将有效内容映射到 PRD 模板，缺口就地标记；已符合模板的稿件保持框架。保留必要图片、来源和历史记录，按内容标准处理编号对应。
2. 在约定范围内修改内容。仅润色时比较行为含义；规则变更时同步引用它的验收与说明。不能用框架迁移作为新增产品决定的理由。
3. 核对未受影响的目标、范围、数值和规则含义是否保持，编号转换后的引用是否有效。对不能核实的原稿内容提示问题，不擅自删掉。
4. 默认另存结果，保留源稿；用户明确要求更新指定文件时执行。重名时用新版本名，不覆盖其他文件。
5. 分别说明模板结构调整和实际内容变更，必要时显示差异。结构检查使用 `template` 或 `draft`，不以输入旧稿的 `existing` 检查替代。

## 多轮与继续

当前文稿保留目标、范围、已明确规则、版本及未决内容，使后续轮次不依赖无限聊天历史。简单修改无须额外生成过程文件。

继续任务时读取最新稿；新会话由用户提供当前文稿或路径，不承诺自动恢复历史对话。若意外读到旧版而无法判断，以用户指定版本为准或说明冲突。

## 结束与失败

正文可理解但存在共同评估项时，可交付初版待核对。产品明确认可后才标为可供团队讨论的初版。核心仍无法理解则标待补充工作稿。任何状态都不等于正式评审通过。

脚本不可用、附件未读取或保存失败时说明实际未完成部分；其他可用内容仍可交付。不能报告不存在的文件或未运行的检查。企业微信、Confluence、Jira 的协作与录入不属于此流程，不加载历史连接器规程或修改宿主连接配置。
