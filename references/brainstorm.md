# 需求探索与机制击穿 (PRD Explore)

## 一、门禁与台账（唯一完整定义）

门禁记录用户决策事实，非模型推断：

| 台账 id | 确认内容 | 通过判据 |
|---|---|---|
| **macro** | 宏观范围与形态 | 宏观四项（用户与角色、背景与现状痛点、目标与成功判据、范围与非目标）已获用户确认 |
| **fr** | 核心 FR 机制击穿 | 本期核心 FR 清单明确，每个关键 FR 的机制候选与代价已获用户裁决 |
| **scope** | 成稿范围与结构 | 已报拟成稿的范围与结构并获用户确认 |
| **review** | 下游审查与消缺 | 四视角下游断点排查与消缺已完成，已交互确认关键决断，达成可交付标准 |

- **留痕与续接**：确认后立即调用 `scripts/gate_state.py --workspace <绝对路径> --clear <id> --evidence "..."` 记账（用户要求直接出稿用 `--waive`）；续接未完成需求先 `--workspace <绝对路径> --read`。
- **一个需求一个工作空间**：台账以工作空间为界。同一需求跨多次会话继续（背景确认后另开会话推具体功能属常见做法）时，工作空间不变，`--read` 即可恢复已确认门禁，**不得因换会话而 `--reset`**；换需求才另开工作空间。命令一律由 AI 执行，用户不手动干预。
- **顺序与复位**：四处按 macro → fr → scope → review 依次记账，前序未记不得跳记后序；`--waive` 后不再接受 `--clear`。`--reset` 是同一工作空间内的例外工具（整本清空），仅用于用户撤回直出稿捷径要重新走门禁，或门禁误记需要重来；因它会丢弃已记门禁，非必要不调用。
- **成稿与交付底线**：macro/fr/scope 三处确认齐备（或已 waive）是成稿前提；满足后按 [成稿与交付](delivery.md) 成稿并执行静态校验；随后按 [下游审查清单](downstream-review.md) 完成四视角审查与消缺并取得 review 确认，方可正式交付或发布 Confluence。

## 二、推演与击穿方法

- **探讨与正文分离**：正文只写“是什么”；候选对比、被否理由与取舍代价沉淀至 `<需求名>_需求探讨.md`。
- **基准与未决**：以用户输入的原始材料（整理的资料、原型、快照或灵感）为基准，明确本期目标与非目标；探索中出现的未决项不当结论写死，其确认状态与去向统一依 [内容约定](prd-standard.md)。
- **第一性归零推演四问（严禁做题家思维，严禁凭先验惯性默写竞品旧实现）**：
  凡进入核心 FR 机制探索（无论全新需求、对标追赶还是历史重构），推演严禁对输入材料进行被动接受与清单级平移，必须强制穿透以下四问：
  1. **意图剥离（Intent vs. Mechanism）**：将“用户真实终态意图（Outcome）”与“既有达成手段（Mechanisms/Forms）”彻底剥离。抹去既有软件的所有按钮、菜单、对话框与历史操作流，直接定义用户不可削减的纯粹业务终态；
  2. **前提审计（Premise Audit）**：既有方案建立在当年哪些历史约束（旧架构限制、控件库缺陷、有限算力、低分辨率、早期操作系统协议等）之上？这些约束在今天的新环境与现代硬件下是否已不复存在？一旦假设瓦解，手段即自动丧失合法性；
  3. **极限动线（The Zero-Friction Limit）**：推导从意图到结果在物理世界中的理论最短操作路径（最少交互步数）。审视每一个弹窗、单选、确认，是必要交互还是推卸系统推断职责？默认给出系统最优解，仅在极少数异常时提供轻量微干预；
  4. **参谋反转（Proactive Inversion）**：AI 绝不做“根据输入清单填空的做题家”，必须主动作为“批判性参谋”。在交出机制候选前，必须主动向用户提交【代差提案】（现状代价 vs 最短路径）；候选之间必须是机制差异而非参数微调，交出代价与推荐倾向，回答“去掉这一步会怎样”。
