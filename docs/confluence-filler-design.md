# PRD Refiner × Confluence 需求落地能力设计（提案）

> 状态：**分阶段实现中**。已在公司 Confluence 7.19.4 上完成 PAT 连通、页面搜索、读取、已有页更新、子页面创建/更新、层级与 HTML 回读，以及表格/正文中的原生跨页面附件图片引用，并加入随 Codex 插件分发的 MCP 启动器；本地图片上传仍待 MCP 提供上传工具后验证。本文档中标注“后期”或“待确认”的能力不能表述为已经完成。

## 0. 背景与问题

企业需求流转的真实路径是：

```text
PM 在 Word / MD 中粗写需求
        ↓
PM 在 drawio / Axure / Figma 中画原型、流程图、状态图
        ↓
按企业 Confluence 需求模板，逐段复制正文、粘贴原型截图、补充遗漏点
        ↓
（可选）在 Jira 中拆需求、建 Issue 并关联 Confluence 页
```

当前 prd-refiner 的核心已覆盖「输入 → 优化 → 六文档本地需求包」，并已验证通过 MCP 更新公司 Confluence 测试页。页面层级映射、成品模板渲染、图片与附件归位尚未完成，因此端到端企业交付仍存在部分人工工作。

本提案把 prd-refiner 的能力从「产出结构化需求包」扩展到「按企业 Confluence 需求模板产出成品页」，让优化结果**直接可落 Confluence**。

## 1. 目标与范围

### 目标

给定产品经理的粗需求（Word / MD）与原型资产（drawio / Axure / Figma / 截图），产出：

1. 一份**遵循企业 Confluence 需求模板结构**的成品页内容；
2. 原型截图、流程图、状态图**按语义归位**到模板对应章节；
3. 草稿遗漏但模板要求的内容：业务决策类进入澄清，可推断类以「AI 建议 / 待确认」显式占位；
4. 以可粘贴（wiki markup / Storage Format / ADF）或可写入（REST API）的形式交付。

### 非目标（本期不做）

- 不替代产品经理做业务决策（沿用核心不变量）；
- 不承诺一次性全自动无确认写入生产空间；
- 不做 Jira 拆票（列入后期，见 §8）；
- 不复制私有原型到插件仓库或公共位置。

### 范围假设（待确认）

- **落点**：以 Confluence 需求页为主，Jira 关联为第二阶段；
- **首期形态**：离线「模板化正文 + 截图归位映射」，在线 API 写入为后续阶段；
- 若实际以 Jira 为主、Confluence 为文档挂载点，需调整 §4 的映射优先级。

## 2. 现状差距

| 环节 | prd-refiner 现状 | 缺口 |
|---|---|---|
| 输入 | Word/MD + 截图/Figma/Axure，任意格式归一化 | 已具备 |
| 建模 | 十二维语义建模 + `UI-xxx` + 证据台账 | 已具备 |
| 澄清 | Plan 模式结构化澄清，`CL-xxx` 追溯 | 已具备 |
| 产出 | 六份固定 Markdown 文档 | **不匹配 Confluence 模板，无法直接粘贴** |
| 资产 | `assets/prototype-images/`、`assets/diagrams/` | **未与 Confluence 章节做映射** |
| 落点 | 本地文件系统；已验证 Confluence 测试页更新、子页创建/更新、层级与回读 | **成品模板层级映射和附件归位尚未验证** |

结论：核心方法论无需重做，缺的是**「目的地适配层」**——把结构化需求模型渲染进企业模板，并把资产与章节对齐。

## 3. 总体思路

保持 AGENTS.md 的「单一业务核心」不变，新增一个下游目的地适配层：

```text
粗 Word/MD + 原型资产
        ↓
skills/prd-refiner（复用：解析 → 十二维建模 → 澄清 → 结构化需求模型）
        ↓
中间产物：机器可读需求模型（JSON，含 FR/BR/DATA/NFR/AC/CL/UI + 来源 + 资产）
        ↓
新目的地适配层 confluence-filler
   ├─ 模板摄取与字段映射（§4.1）
   ├─ 原型资产归位（§4.2）
   ├─ 缺失点补充（§4.3）
   └─ 渲染与写入（§4.4）
        ↓
Confluence 需求页（粘贴文本 / 页面草稿 / API 写入）
```

关键决策：

1. **不改核心、不复制规则**：prd-refiner 核心输出一个稳定 ID 化的「需求模型」，适配层只做「模型 → 模板」的渲染与映射，遵守「不把 SKILL.md / 规则 / 模板复制进适配目录」的仓库不变量。
2. **模板即输出 schema**：企业 Confluence 需求模板取代六文档 Markdown 成为最终呈现；六文档降级为「可选的中间/追溯产物」，不再强制作为交付物。
3. **证据分级贯穿到页面**：Confluence 成品页内保留「原始事实 / 原型观察 / 产品经理确认 / AI 建议 / 待确认」的可见标记（或至少对待确认项醒目标注），不把 AI 推断伪装成结论。

## 4. 能力拆解

### 4.1 模板摄取与字段映射

企业需求模板是适配的核心。模板来源三选一或组合：

| 来源 | 说明 | 能力要求 |
|---|---|---|
| 粘贴模板结构 | 用户粘贴模板的标题/字段/表格骨架 | 文本解析，最轻量 |
| 读取已有 Confluence 页 | 以某个标准需求页为蓝本 | 宿主可访问的 Confluence 连接（API/MCP/浏览器） |
| 上传导出的模板 | Word/HTML 导出的模板文件 | 文档解析 |

流程：

1. 摄取模板，提取**章节序列、必填字段、表格列、宏占位**（如状态、标签、评审人字段）；
2. 生成「模板字段 ↔ 十二维」映射建议，例如：

| 模板章节 | 映射十二维 | 示例 ID |
|---|---|---|
| 背景与目标 | 3.1 背景目标 / 3.2 范围非目标 | FR-xxx、目标/指标 |
| 角色与权限 | 3.3 角色场景 / 3.7 权限 | 角色表、权限矩阵 |
| 功能需求 | 3.5 主流程与规则 / 3.6 数据状态 | FR/BR/DATA |
| 页面与交互 | 3.11 PRD-原型关联 | UI-xxx |
| 异常与边界 | 3.8 异常边界 | 异常表 |
| 验收标准 | 3.10 验收 | AC-xxx |
| 非功能 | 3.9 非功能 | NFR-xxx |

3. **映射结果需产品经理确认**（沿用「AI 建议不可直接成为结论」），确认后固化为该企业的模板配置，可复用。

### 4.2 原型资产归位

把原型资产按语义定位到模板章节，而不是堆在文末。

| 资产 | 解析方式 | 归位目标 |
|---|---|---|
| drawio `.drawio` | 优先解析 XML 结构（节点/连线/文本），无结构时导出图片 | 流程图/状态图 → 业务流程、状态迁移章节 |
| Axure HTML / 截图 | 遍历可访问页面与交互，或读截图 | 页面截图 → 页面与交互章节 |
| Figma | 截图 / 宿主可访问的 API/MCP（只读） | 页面截图、Frame → 页面与交互章节 |
| 独立截图 | 图片识别 | 按 `UI-xxx` 语义归位 |

输出产物：

- 「资产 → 章节」归位清单；
- 成品页内以**图片引用/macro 占位**形式插入到对应章节；
- 无法归位或用途不明的元素标「待确认」，不强行塞入。

沿用原型分析规范：仅记录直接可观察内容；交互意图、业务约束仍需澄清，不因原型存在就写成已确认规则。

### 4.3 缺失点补充

「补充没想到的点」拆成两类，处理边界不同：

| 类型 | 定义 | 处理 | 证据标记 |
|---|---|---|---|
| 业务决策缺口 | 模板要求的字段/章节，草稿缺失且答案影响产品行为 | 进入结构化澄清，生成 `CL-xxx` | 产品经理确认 |
| 可推断缺口 | 模板要求、草稿可推断或为工程性/编辑性内容 | 生成候选内容 + 待确认标记 | AI 建议 / 待确认 |
| 形式性字段 | 版本、状态、评审人等元信息 | 自动填充模板默认值并提示核对 | 产品经理确认 |

关键红线：**不得把 AI 推断写成品经理已确认**。模板里所有「必填但草稿没有」的内容，要么澄清、要么以显式「待确认/AI 建议」占位，交付说明中汇总。

### 4.4 渲染与写入

按阶段提供递进交付形态：

| 形态 | 说明 | 依赖 | 阶段 |
|---|---|---|---|
| 可粘贴 wiki markup | 旧版 Confluence 存储标记（`{panel}`/表格/`{info}`） | 无 | MVP |
| Storage Format（XHTML） | 新版存储格式，可直接粘贴或经 API | 无 | MVP |
| ADF（JSON） | Atlassian Document Format，供 API/编辑器导入 | 无 | MVP |
| MCP 页面更新 | 更新指定测试页并回读版本和正文 | 公司 Confluence PAT；锁定兼容依赖 | 已完成最小验证 |
| MCP 子页创建/更新 | 在指定 space/parent 下创建页面、更新正文并回读层级 | 同上 | 已完成最小验证 |
| MCP Confluence 图片引用 | 在表格和正文中用 `ri:attachment + ri:page` 引用既有图片，并通过 `body.view` 确认解析为 `<img>` | 同上 | 已完成服务端最小验证 |
| MCP 本地图片上传 | 上传无可访问 URL 的本地图片并回读附件清单 | 需补充 MCP 上传工具 | 下一阶段 |
| 在线预览/回写 | 生成写入预览，经 PM 确认后执行并记录结果 | 同上 | 设计已确定，待完整实现 |

渲染原则：

- 保留稳定 ID（`FR/BR/DATA/NFR/AC/UI`）作为页内锚点或不可见注释，维持可追溯；
- 待确认项用醒目的 `状态宏`（如「待确认」面板）标注，不静默省略；
- 六份 Markdown 文档中的 `traceability-matrix.md` 可作为页面附录或独立子页，不强制散入正文。

## 5. 与现有 prd-refiner 的关系

- **复用**：任意格式归一化、十二维检查、证据台账、Plan 模式澄清、编号追溯、前后同尺评分，全部复用。
- **新增**：仅新增「模板摄取 → 字段映射 → 资产归位 → 渲染/写入」的目的地适配层，以及一个机器可读的需求模型中间产物。
- **不变**：显式启动、不自动触发、不替 PM 做决策、保留 `CL-xxx` 追溯、token 不入库、连接器只读优先。
- **仓库位置**：适配层作为独立技能/目录（如 `skills/confluence-filler/` 或 `skills/prd-refiner/destinations/`），只持有模板映射与渲染逻辑，不复制 prd-refiner 的规则与模板。

## 6. 关键决策与边界（待确认项）

以下决策点需在实现前与产品/用户确认，本提案给默认建议：

1. **中间产物**：是否保留六文档 Markdown 作为交付物，还是仅作为内部追溯？默认：降级为可选，追溯矩阵作为页面附录。
2. **模板来源**：企业模板以哪种方式提供？默认：先支持「粘贴模板结构」+「读取已有页」，上传导出文件其次。
3. **写入权限**：在线写入是否允许直接发布，还是只创建草稿待人工复核？默认：只创建草稿，发布由 PM 手工执行。
4. **待确认项的页面呈现**：页内用状态宏标注 vs 单独「待确认清单」面板？默认：两者结合，页内标 + 文末汇总。
5. **Confluence 访问方式**：宿主浏览器/MCP/API 连接器的选择取决于目标企业环境与宿主平台能力。
6. **多模板/多空间**：是否需支持不同团队/空间的多套模板配置？默认：模板配置按空间或团队可保存复用。

## 7. 端到端示例流程

```text
1. PM 显式启动 $prd-refiner（或 $confluence-filler 子入口）
2. 提供：粗 Word/MD + drawio 流程图 + Figma/Axure 截图
3. 提供/选择：企业 Confluence 需求模板（粘贴结构或读已有页）
4. 插件解析建模，提出「模板字段 ↔ 十二维」映射建议 → PM 确认
5. 插件识别缺失/歧义/冲突 → Plan 模式澄清（高影响单独问，独立项成组问）
6. 插件把原型资产归位到对应章节，未归位项标待确认
7. 插件渲染：可粘贴 wiki markup / Storage Format / ADF + 待确认清单 + 归位清单
8. （后期）插件经 API 在目标 space 创建页面草稿，PM 复核后发布
9. （后期）插件按 FR 生成 Jira Issue 草稿，关联 Confluence 页
```

## 8. 分期路线

| 阶段 | 内容 | 验收要点 |
|---|---|---|
| MVP | 模板摄取（粘贴结构）+ 字段映射确认 + 六文档模型 → wiki markup/Storage Format/ADF 渲染 + 资产归位清单 + 待确认标注 | 输出可直接粘贴且符合模板；待确认项不遗漏 |
| 增强 | 读取已有 Confluence 页作蓝本；drawio XML 结构解析；ADF 导入支持 | 结构图、状态图能自动归位到正确章节 |
| 集成 | Confluence REST API 创建页面草稿；Figma 只读连接器 | 认证由宿主管理，不直接发布 |
| Jira | FR → Epic/Story/Task 拆票；AC → 验收；双向链接 Confluence 页 | 拆票结果可复核、可追溯 |

## 9. 风险与开放问题

- **模板异构**：各企业模板差异大，映射确认是必经环节，无法纯自动；需评估映射确认的成本是否低于手工搬运。
- **Confluence 版本差异**：wiki markup 与 Storage Format 并存，需按目标实例版本选择渲染格式。
- **认证与安全**：在线写入涉及 Confluence token，必须在宿主环境管理，不入库、不进日志。
- **资产隐私**：原型截图仅在本地处理，写入时由 PM 决定是否上传为页面附件。
- **效果度量**：如何衡量「搬运成本下降」？建议沿用前后同尺评价（下游可用性 + 人工追问次数），并记录「从草稿到页面发布的耗时/操作次数」作过程指标。

## 10. 落地检查点

实现前需确认：范围假设（§1）、六个关键决策（§6）、模板来源与 Confluence 版本、目标宿主的访问方式。实现中遵守：不改核心、不复制规则、不提前声明平台已验证、token 不入库。
